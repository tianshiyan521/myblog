前两课用的是练习台——接口文档齐全、地址现成。

但真实的场景往往是另一种样子：

- **没有接口文档**（或者文档早就过期了）
- **不知道接口地址**（客户端是 C# 外壳，前端代码里翻遍了也没有）
- **不会抓包**（环境装不了 Charles/Fiddler，证书也搞不定）
- 协议是**二进制**的，看不懂

这一课讲**怎么在这种条件下把私有协议完整扒出来**，并做出 36 条用例的自动化测试。

全程没用抓包工具，也没装证书。

<!-- more -->

## 一、起点：一个"打不开"的黑盒

被测对象是一个游戏启动器（C# / .NET + WebView2）。

它的登录界面是 WebView2 加载的 H5，但**H5 只负责收集输入**，真正的 HTTP 请求由 C# 宿主发出。

这意味着：**翻遍前端代码也找不到接口地址。** 打开开发者工具看 Network，一条请求都没有。

常规思路是抓包。但如果：

- 客户端的网络请求走了自定义的 HTTP 客户端，证书代理装不上
- 手上没有合适的环境
- 或者单纯就是不想为了测一个接口去学抓包工具

**那就换一条路。**

---

## 二、★ 核心思路：客户端自己把请求写进了日志

**很多客户端在 Debug/Detail 日志级别下，会把每个 HTTP 请求和响应明文写进日志文件。**

这比抓包更省事：

| | 抓包 | 读日志 |
|---|------|--------|
| 装工具 | 需要 | **不需要** |
| 配代理 | 需要 | **不需要** |
| 装证书 | 需要 | **不需要** |
| 历史数据 | 只有开启后的 | **历史累积的，一次能拿到几十上百次真实交互** |

### 第 1 步：定位日志目录与级别

```bash
ls -la "<安装目录>"          # 找 Logs / logs 目录
ls -lat "<安装目录>/Logs" | head -20
tail -100 "<最新的log>"
grep -c "HTTP Request" <log>
```

**结果**：日志目录里躺着 47 个日志文件，里面有 `[DETAIL] HTTP Request >>>` / `HTTP Response <<<` 段，Method、URL、Header、Body 全都在。

**如果日志里没有请求明细，说明级别不够**——去配置文件或环境变量里找 `LogLevel=Detail/Debug`。

### 第 2 步：批量提取（用脚本，别用 grep）

日志常有少量 NUL 字节导致 `grep` 判定为 binary，要用 `grep -a`。**更稳的是直接写 Python 脚本**：

```python
with open(path, 'rb').read().decode('utf-8', 'ignore') as raw:
    # 按 "HTTP Request >>>" / "HTTP Response <<<" 切块
    # 提取 Method / URL / Headers / Body / Status
    # 按 URL + 关键 Header 去重汇总
```

> **关键点**：多个业务接口常常**共用一个地址**，靠 HTTP 头（这里是 `CID`）区分。
> 统计时必须把 Header 一起带上，否则会把几十个接口当成一个。

---

## 三、扒出来的结构：一个网关 + CID 路由

跑完提取脚本，登录链路的结构清楚了：

| 环节 | 地址 | 路由头 |
|------|------|--------|
| **登录** | `POST http://<网关>:9511/` | `CID: 1396` |
| **换 access token** | 同上 | `CID: 1401` |
| **公告** | 同上 | `CID: 1527` |
| **心跳** | 同上 | `CID: 1409` |
| **远程配置** | `GET http://<CDN>:9000/raptor-client-test/...` | 静态 CDN |
| **游戏清单** | 同上 `.../Manifest.json` | 附带 `.md5` 做完整性校验 |

**网关用 HTTP 头里的 CID 做消息路由**：

- 不存在的 CID → `HTTP 500  no route for cid 9999`
- 不带 CID → `HTTP 500  no route for cid -1`

这个设计很常见：**一个入口地址 + 头部路由**，比 RESTful 的路径路由更省连接数。

## 四、识别协议编码

看 body 的十六进制：

```bash
od -c body_line | head
```

特征：出现连续可读字符串（账号、密码）+ 可疑的控制字节。

**这是 protobuf。** 判断依据：

- `tag = (field << 3) | wt`
- `wt = 2` 是长度分隔（`[tag][len][data]`）
- `wt = 0` 是 varint

**判别字段号时注意**：`(field<<3)|2` 换算，**≥16 的字段标签是两个字节**（如 `0x82 0x01` 是字段 16）。按单字节读会字段错位。

---

## 五、★ 最容易卡死的一步：日志吃掉了字节

### 现象

日志里看到的登录请求体：

```
[长度][账号] [0x12][长度][密码] ...
```

**照着这个发出去 → `code=38`（参数错误）。**

### 排查过程

日志把 body 当**字符串**打印，无法用 UTF-8 表示的字节会变成 `EF BF BD`（U+FFFD 替换字符），**每个丢失字节膨胀成 3 字节**。

**长度校验法**：

```
原始长度 = 日志长度 - 2 × 丢失字节数
```

**语义校验法**（判断首字段是"标签"还是"长度"）：

拿同一接口的**多个不同输入**的请求体对比：

- 账号 `tester01`（8 位）→ 首字节 `0x08`
- 账号 `tester0009`（10 位）→ 首字节 `0x0A`

**首字节随输入长度变化 → 它是长度**（而不是标签）。

### 真相

protobuf 字段 1 的 string 类型标签是 `0x0A` —— **正好是换行符，被日志的行处理吃掉了。**

```
日志里看到：  [长度][账号] [0x12][长度][密码] ...
真正要发的：  0x0A [长度][账号] [0x12][长度][密码] ...
              ↑ 补这个
```

**判据**：补上 `0x0A` 后服务端返回成功，去掉则返回"参数错误"。

> ⚠️ **对每个接口都要做这个验证，不要只验证一个。** 不同接口的首字段可能不一样。

## 六、用 Python 复现并验证

```python
def _varint(n):
    out = b''
    while True:
        b = n & 0x7f
        n >>= 7
        out += bytes([b | (0x80 if n else 0)])
        if not n:
            return out


def f_len(field, v):
    """构造 protobuf 长度分隔字段：[tag][len][data]"""
    if isinstance(v, str):
        v = v.encode('utf-8')
    return _varint((field << 3) | 2) + _varint(len(v)) + v
```

**请求头必须照抄**：

```
Content-Type: application/octet-stream
CID: 1396
User-Agent: RaptorLauncher/0.1
```

> 网关往往靠自定义头做**消息路由**，缺了会返回 500（`no route for cid -1`）。

## 七、摸清错误码字典（生成用例的前提）

**做法：固定协议结构，只改一个输入，观察响应码变化。**

必测：正确值 / 密码错 / 密码空 / 账号空 / 账号不存在 / 超长 / 特殊字符 / 大小写 / 前后空格 / 缺字段 / 空 body。

### ⚠️ 第一个认知：不用假设错误码和 HTTP 状态码一致

实测结果：

| 输入 | HTTP | 响应体 code |
|------|------|------------|
| 密码错误 | 200 | 14 |
| 账号不存在 | 200 | 13 |
| 账号为空 | 200 | 39 |
| 密码为空 | 200 | 10 |
| 协议字段缺失 | 200 | 38 |
| 旧 token / 伪造 token（字段可解析） | **499** | 35 |
| 不存在的 CID | **500** | （纯文本） |
| GET 方法 | **501** | （纯文本） |

**业务错误统一 HTTP 200，成败只在响应体 code。**

所以脚本里**绝对不能**用 `assert r.status_code == 200` 判断用例通过——那是自欺欺人。

## 八、★★ 踩得最狠的坑：把 499 当成"限流"去重试

这是这次动手**代价最大**的一个误判，值得单独讲。

### 现象

某伪造 token 的用例期望 `HTTP 200 + code=1`，实际稳定得到 `HTTP 499 + code=35`。

当时的 `_retry` 写了：

```python
if last.status_code in (499, 502, 503, 504):
    time.sleep(...); continue   # 当作限流，退避重试
```

于是不停地重试，最后返回 499。**用例判定随机飘，查了半天查不出原因。**

### 打脸证据

关键动作：**固定输入、拉开时间间隔重复打。**

| 请求体 | HTTP | body | 说明 |
|--------|------|------|------|
| `0x0A` + `"A"×44` | **499** | `08 23` → code=35 | token 字段**能解析**，值无效 |
| 去掉 `0x0A` 的 44 个 A | **200** | code=1 | token 字段**解析不出来** |
| `0x0A` + 空串 | **499** | code=35 | 字段能解析，值为空 |
| 空 body | **200** | code=1 | 完全无字段 |

- **同一伪造 token，间隔 1.5 秒连打 8 次，8 次全是 499** —— 与频率完全无关
- 反向验证：40 次错误密码、30 次高频正确登录、15 个不同账号 → **完全没有触发任何限流**

### 真实规律

**以"字段能否解析"分层：**

| 输入 | HTTP | code | 走了哪层 |
|------|------|------|---------|
| token 字段**可解析**但值无效 | **499** | 35 | 协议层拦截 |
| token 字段**解析不出**（缺 0x0A 标签、空 body） | **200** | 1 | 业务层 |

**499 的真实含义是："token 字段可解析但验证失败"** —— 网关在协议层直接拒绝，不再往下走业务逻辑。

### 教训

```python
def _retry(fn, times=3, wait=0.8):
    """只对真正的服务端抖动（502/503/504）做退避重试。
    不要在这里重试 499！
    """
    last = None
    for i in range(times):
        last = fn()
        if last.status_code not in (502, 503, 504):
            return last
        time.sleep(wait * (i + 1))
    return last
```

**四条规范：**

1. `_retry` **只对 502/503/504 重试**。499 必须原样返回给用例判定
2. 判定这类用例要**同时断言 HTTP 状态码和 code**，不能只看 code
3. **任何重试逻辑的前提，是先证明"这是瞬时抖动"**。看到错误码就重试，等于用一个错误假设掩盖真实的协议行为
4. **验证是否限流的标准动作**：固定输入 + 拉大间隔重复打若干次。每次都一样 → 确定性行为

> 这个坑还让整体耗时从 20.6s 降到 6.2s —— 因为不再做无意义的退避等待。

## 九、识别会话机制（易漏，会导致用例互相干扰）

用两个维度测：

**① 时效**：登录取 token → 等 2/5/10 秒再使用，看是否失效

**② 互踢**：登录取 T1 → 跨秒再登录 → 用 T1，看是否被顶掉

### 实测发现：单会话互踢

- token 按**秒**派生，**同一秒内重复登录会得到相同 token**
- **一旦发生一次产生新 token 的登录，旧 token 立即作废**
- 拿旧 token 去换 access token → `HTTP 499` + `code=35`

⚠️ **同秒内重复登录得到相同 token，此时"互踢"测不出来** —— 必须**跨秒**（`sleep 1.3s` 以上）才能复现。

### 对自动化的影响

**一旦发现互踢，所有用例的 token 都必须当场登录当场用，不能跨用例复用。**

这解释了启动器为什么在拉起游戏前**一定要再刷一次 token**。

## 十一、顺手发现的几个问题

写用例过程中撞到的，都提给了开发：

1. **账号大小写敏感** —— `TESTER01` 被判为"账号不存在"，玩家输错大小写时错误提示会误导（应提示"账号或密码错误"而不是"账号不存在"）
2. **账号前后空格未 trim** —— 手机端复制粘贴常带空格，建议服务端做 trim
3. **版本号完全不校验** —— 传空、传 `9.9.9` 都能登录成功，版本门槛没生效
4. **昵称字段可任意伪造** —— 客户端传的昵称服务端照单全收（当前返回账号数据，风险低，但字段本身无效）

> **注意第 1 条**：这类问题严格说不是"功能 bug"，而是**错误提示的语义问题**。但它会真实地误导用户、增加客服工单。**能发现这类问题，说明你在用"玩家视角"看接口，而不只是在跑用例。**

## 十二、这一课的方法论总结

| 步骤 | 要点 |
|------|------|
| 1. 找数据源 | 客户端 Detail 日志 > 抓包（省去工具、证书、代理） |
| 2. 批量提取 | 用脚本，不用 grep；**Header 要一起统计** |
| 3. 识别编码 | protobuf：`(field<<3)\|wt`；≥16 字段标签是 2 字节 |
| 4. 找丢字节 | 长度校验 + 语义校验（改输入看首字节变化） |
| 5. 复现验证 | 请求头照抄（网关可能靠自定义头路由） |
| 6. 摸错误码 | 固定结构改单一输入；**HTTP 200 不代表成功** |
| 7. 判重试 | **先证明是瞬时抖动**；只重试 502/503/504 |
| 8. 识别会话 | 测时效 + 互踢；注意同秒 token 相同 |

## 合规边界

这一课的所有操作都在**客户授权范围内的测试环境与测试账号**上完成：

- 只测登录/鉴权/更新链路，**不碰注册、改密、支付等破坏性操作**
- 不绕过任何反作弊机制
- 测试产生的接口信息不用于测试以外的用途
- 对外分享时，**网关地址、账号、公司项目名全部脱敏**

> **这一条是底线。** 逆向能力本身是中性的，但用在未授权的目标上就是另一个性质了。做测试的边界永远只有一条：**授权范围之内。**
