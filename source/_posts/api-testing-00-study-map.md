## 一、起点诊断

| 层级 | 能力项 | 状态 | 依据 |
|------|--------|------|------|
| **L1 协议地基** | HTTP 方法、状态码、Header、JSON、鉴权 | ✅ 已掌握 | 有基础 |
| **L2 工具链** | Postman、Apifox、抓包分析、接口文档 | △ 待补强 | 工具熟练度不足 |
| **L3 用例设计** | 等价类、边界值、场景串联、异常安全 | ❌ **最大缺口** | 此前是"照文档写脚本"，非独立设计 |
| **L4 自动化** | requests、pytest、断言、数据驱动、报告 | ✅ 已掌握 | 能写脚本 |
| **L5 工程化** | 分层框架、多环境、Mock、CI、契约测试 | △ 待补强 | 有思路，未落地真实项目 |

**结论**：补齐 **L3（用例设计思维）+ L2（工具熟练度）+ L5（工程落地）**，即可打通完整能力链。

> ⚠️ 注意 L3 被标为"最大缺口"，而且它是**认知层**的问题，不是技术层的。
> 会写 `requests.post()` 不等于会设计用例。**这是两条完全不同的能力。**

## 二、接口测试是什么

**本质**：绕开界面，直接验证系统之间的"契约"——**按约定发什么，就必须按约定还什么，无论输入正常还是垃圾。**

后半句是关键。很多人只测了"正常输入正确返回"，但**真正的 bug 都藏在异常输入里**。

### 为什么比 UI 测试更值得投入

| | 接口测试 | UI 测试 |
|---|---------|--------|
| **时机** | 后端交付即可测，不等前端 | 必须等界面完成 |
| **速度** | 单接口 100ms 级 | 单用例 30s 级 |
| **稳定性** | 业务逻辑变了才挂 | 改个按钮挂一片 |
| **覆盖度** | 能打异常分支、越权、边界 | 只能覆盖用户点得到的路径 |

**测试金字塔占比**：接口测试 **60~70%**，单元 **20~30%**，UI **10%**。

## 三、测什么：一个接口的五大维度

沿这五条线展开，用例就不会漏：

| # | 维度 | 具体校验点 |
|---|------|-----------|
| 1 | **功能正确性** | 正常入参返回预期结果、字段值准确、单据真的落库 |
| 2 | **参数校验** | 必填缺失、类型错误、长度边界、特殊字符、多余字段 |
| 3 | **业务逻辑** | 状态流转合法性、接口依赖串联、幂等性、并发一致性 |
| 4 | **异常与容错** | 错误码语义区分、超时重试、服务降级、重复提交 |
| 5 | **安全与权限** | 鉴权失效、水平/垂直越权、注入、敏感信息泄露 |

## 四、完整工作流

```text
① 拿到接口信息   Swagger / 接口文档 / 抓包反推 / 找开发要 cURL
② 拆解契约       入参出参字段、错误码表、依赖了哪些其他接口
③ 设计用例       按五大维度展开，而非想到哪测到哪
④ 执行           Postman 手工验证 → Python 代码自动化
⑤ 校验响应       分层校验（见下）
⑥ 沉淀           用例入库 → 纳入回归集 → CI 自动触发
```

### 分层校验：缺一层就可能漏 bug

| 层 | 验什么 | 例子 |
|---|--------|------|
| **协议层** | HTTP 状态码 | 200 / 401 / 500 |
| **业务层** | 响应体业务码 | `code == 0` |
| **数据层** | 字段值与格式 | `data.level == 12`、关键字段非空 |
| **副作用层** | 数据库/下游真的变了 | 查库确认金币真的扣了 |

## 五、三个高频翻车点

### 1. 只测正常流程

开发写代码时想的是"正常走通"，**bug 都藏在异常分支里**。

### 2. 用例互相污染

用例 A 创建的数据被用例 B 用掉，执行顺序一变就全红。

**必须有数据隔离策略**：每条用例自带前置，不依赖其他用例的副作用。

### 3. 断言太弱

```python
assert r.status_code == 200   # ← 等于没测
```

游戏服务端的网关尤其如此——**很多游戏网关的 HTTP 状态码永远是 200**，真实成败藏在响应体里。

```json
// 看起来成功了，其实等级不够
{ "code": 50002, "msg": "level not enough", "data": null }
```

## 七、下一步该补什么

按这五个缺口排优先级：

| 优先级 | 补什么 | 怎么补 |
|--------|--------|--------|
| **P0** | 用例设计思维 | 用真实接口把五大维度各出一遍，请人 review |
| **P0** | 接口文档没有时怎么拿 | 抓包反推 / 读日志（第 3 课已覆盖） |
| **P1** | 数据驱动 | 用例挪到 Excel/YAML，做到"加用例不改代码" |
| **P1** | 报告与 CI | pytest + Allure + GitHub Actions |
| **P2** | 契约测试与 Mock | 前后端解耦测试、并行开发 |

> **一句实话**：接口测试的"难"不在写代码，在于**你没测过的异常情况，你想不到**。
>
> 所以最有价值的投入永远是——**去把别人踩过的坑变成自己的用例**。
