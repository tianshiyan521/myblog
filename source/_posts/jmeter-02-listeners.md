跑压测容易，**看懂结果难**。

这篇整理 JMeter 的 6 种监听器，以及它们各自适合什么阶段用。核心原则只有一条：**监听器很吃资源，用错了会污染测试结果。**

<!-- more -->

## 一、核心理念：监听器是"观察者"，也会"干扰"

JMeter 的监听器在收集数据、渲染界面时都要消耗 CPU 和内存。**这些开销和被测系统抢资源。**

所以监听器的使用有个明确的取舍：

> **调试时要看得清楚，压测时要跑得干净。** 这两个目标对立。

---

## 二、6 种核心监听器

### 1. 聚合报告（Aggregate Report）⭐ 最常用

压测结果的**核心仪表盘**，一次给出所有关键指标：

| 指标 | 关注点 |
|------|--------|
| Samples / Average / Median | 基础统计 |
| **90% Line** | **性能 SLA 看这个** |
| Min / Max | Max 很大说明有抖动 |
| **Error%** | **必须 0%** |
| **Throughput** | 吞吐量（请求/秒） |

### 2. 汇总报告（Summary Report）

和聚合报告类似，但**输出更简洁**，适合快速扫一眼。

### 3. 察看结果树（View Results Tree）

逐个请求看详情：请求头、请求体、响应头、响应体。

**调试脚本必用**，但**绝不能在大规模压测时开**——250 个请求还能接受，10 万个请求会直接把 JMeter 卡死。

### 4. 图形结果（Graph Results）

把响应时间画成曲线，能直观看到**响应时间的抖动情况**。

比聚合报告的单一数字更能反映"稳不稳"。

### 5. 断言结果（Assertion Results）

只看断言失败的请求，调试断言逻辑时用。

### 6. 后端监听器（Backend Listener）— 进阶

**企业级方案**：

```
JMeter → Backend Listener → InfluxDB → Grafana
```

JMeter 把指标实时推给 InfluxDB，Grafana 做大屏可视化。**压测时可以实时看曲线，不用等跑完。**

---

## 三、分阶段选择监听器

| 阶段 | 推荐监听器 | 原因 |
|------|-----------|------|
| **脚本调试** | 察看结果树 + 断言结果 | 需要看请求响应细节 |
| **基准测试** | 聚合报告 + 图形结果 | 分析性能基线 |
| **正式压测（CLI）** | 简单数据写入器 + 后端监听器 | 保存结果 + 实时大盘 |
| **压测后分析** | HTML 报告（`-e -o`） | 可视化 + 统计 |

### CLI 模式黄金组合

```bash
jmeter -n -t plan.jmx \
       -l result.jtl \        # ← 保存原始结果
       -e -o report/ \        # ← 生成 HTML 报告
       # + 配置后端监听器      # ← 实时大盘
```

## 四、实测数据：一次真实的压测

### 测试配置

- 线程数：10 | Ramp-Up：3s | 循环：5 次
- 总样本数：**250**（5 个采样器 × 50 次）
- 运行时长：约 10 秒

### 各接口表现

| 接口 | 样本数 | 错误率 | 平均响应 | 中位数 | 90% Line | 吞吐量 |
|------|--------|--------|----------|--------|---------|--------|
| GET 获取帖子列表 | 50 | 0% | 430.9ms | 418.5ms | 668.8ms | 5.7/s |
| GET 获取单条帖子 | 50 | 0% | 250.6ms | 219.0ms | 251.9ms | 6.0/s |
| POST 创建帖子 | 50 | 0% | 342.4ms | 314.0ms | 401.8ms | 5.9/s |
| GET 百度首页 | 50 | 0% | 26.7ms | 23.0ms | 43.0ms | 6.2/s |
| GET 故意 404 | 50 | **100%** | 234.9ms | 220.5ms | 257.9ms | 6.1/s |
| **总计** | **250** | **20%** | **257.1ms** | **232.5ms** | **469.0ms** | **26.2/s** |

### 关键发现

**① 百度首页最快（26.7ms）** —— 静态页面 + CDN 加速

**② 帖子列表最慢（430.9ms）** —— **返回 100 条数据，数据量大**

> 这是个很典型的性能瓶颈特征：**响应时间与数据量正相关**。
> 优化方向也很明确——分页、减少返回字段、加缓存。

**③ 404 请求失败但不影响其他请求**

线程组设了 `continue`（而非 `stop thread`），单个请求失败不会中断整个压测。

⚠️ **这个设置很关键**：如果设成出错就停，第一个 404 就会让整个测试挂掉，其他接口的数据全都拿不到。

**④ 20% 错误率完全来自 404 场景** —— 符合预期

> **看报告时一定要追查错误率来自哪里。**
> 20% 的错误率听起来很吓人，但定位到"全部来自一个故意设计的 404 用例"，就完全正常。
> **不追来源就下结论，是性能测试最常见的误判。**

## 五、踩坑记录

| 问题 | 原因 | 解决 |
|------|------|------|
| HTTPS 全失败（100% 错误） | JMeter + Java 11 的 SSL 证书兼容问题 | 改用 HTTP 协议测试目标 |
| httpbin 无限重定向 | httpbin 强制 301 跳 HTTPS | 换 jsonplaceholder + baidu |
| Git Bash 运行报错 | shell 脚本路径/编码问题 | 用 PowerShell + `jmeter.bat` |

> 第一条踩坑值得记一下：**JMeter 报 100% 错误的时候，先怀疑工具链，别急着怀疑被测系统。**
> 尤其是 HTTPS 相关的问题，Java 版本、证书库（cacerts）、TLS 版本都可能出问题。
