面试游戏测试时，基础概念和 BUG 管理这两块几乎必问。它们不难，但最容易答得"飘"——很多人能背出定义，却举不出自己项目里的例子。

这篇把这两类题的答题框架整理出来，每题都配了具体的答题思路。

<!-- more -->

## 一、基础概念类

### Q1：游戏测试和软件测试有什么本质区别？

标准答案会说"游戏测试多了体验维度"，但这样答太干。我给一个更好用的框架：

**核心区别一句话：软件测试验证"对不对"，游戏测试还要验证"好不好玩"。**

| 维度 | 软件测试 | 游戏测试 |
|------|---------|---------|
| 目标 | 功能正确、无 BUG | 功能正确 + 体验流畅 + 趣味性 |
| 判定标准 | 客观（通过/不通过） | 主客观混合，主观占比大 |
| 性能关注 | 响应时间、并发量 | 帧率、卡顿、发热、耗电 |
| 兼容性 | 浏览器/系统版本 | 机型 + GPU + 分辨率 + 操作方式 |
| UI 测试 | 布局正确、交互正常 | 还要看美术表现、动效节奏、操作手感 |
| 用户行为 | 按预期路径操作 | 玩家会做各种"不按套路出牌"的事 |

**关键在举例。** 面试官想听的是你能不能划清边界：

- **软件测试思维就够的场景**：商城购买道具 → 验证扣钻石正确、道具到账、异常处理。这跟测电商支付没本质区别。
- **必须用游戏测试思维的场景**：多人同屏战斗 → 不仅要验证胜负结算正确，还得关注：
  - 20 人同屏时帧率是否稳定（纯软件测试不测帧率）
  - 技能特效是否遮挡关键 UI（美术 + 交互的交叉问题）
  - 击杀反馈的震动/音效/飘字节奏是否"爽"（纯体验层）
  - 低端机玩 30 分钟后是否烫手（游戏独有维度）
  - 玩家连打 10 场是否无聊（留存与疲劳度）

一句话总结：**软件测试保证"能用"，游戏测试还得保证"玩家愿意一直用"。**

### Q2：什么是冒烟测试？

对新版本做**基础功能快速验证**，核心功能可用才进入深入测试。

我喜欢用开发视角解释它存在的意义：如果连登录都进不去，你再花两天测活动玩法全是白费。冒烟测试就是**用最小成本判断"这版值不值得测"**。

### Q3：Monkey 测试适合游戏吗？

随机生成大量操作输入，**适合发现崩溃类问题，对逻辑性 BUG 帮助有限**。

游戏里的实际用法是：版本提测时先跑一轮 Monkey 看有没有必崩的点，跑通过后再开始正式用例。它替代不了用例，但能当一个廉价的兜底网。

## 二、BUG 管理类

### Q4：BUG 严重等级怎么划分？

五级划分，每级都要能举出自己项目的例子。下面用 SLG 类项目举例：

| 等级 | 说明 | 举例 |
|------|------|-----------|
| 致命（Blocker） | 崩溃 / 核心流程阻断 | 点击核心玩法入口直接闪退，所有玩家无法进入该玩法 |
| 严重（Major） | 核心功能不可用 | 商城购买道具扣了钻石但道具未到账，影响付费体验 |
| 一般（Normal） | 功能异常但不阻塞 | 自动挂机切到后台 5 分钟后停止攻击，但 UI 仍显示"挂机中" |
| 轻微（Minor） | 不影响功能的瑕疵 | NPC 名字"迅猛龙"写成"讯猛龙"，一看就出戏 |
| 建议（Suggestion） | 体验优化 | 背包已满的提示只停留 0.5 秒，来不及看清 |

> **记住这个口诀**：致命 = 不能玩，严重 = 核心玩不了，一般 = 能用但不对，轻微 = 能用但不爽，建议 = 能用但可以更好。

⚠️ **一个常见坑**：等级不是由"技术上多严重"决定，而是由**业务影响面**决定。同一个空指针，崩在登录页是致命，崩在某个冷门成就弹窗上可能就是一般。提 BUG 时把"影响多少用户、走哪条路径能碰到"写清楚，等级自然站得住。

### Q5：BUG 报告怎么写才算合格？

模板：

```
标题：简要描述问题（建议的写法见下）
版本：发现时的版本号
设备：机型 / PC 配置 / 系统版本
步骤：1.打开游戏 → 2.点击XX → 3.……
实际结果：发生了什么
预期结果：应该发生什么
附件：截图 / 日志 / 录屏
```

**标题是最容易被低估的一环。** 对比一下：

- ❌ `领地争夺有 bug` —— 等于没说
- ❌ `结算有问题` —— 还是等于没说
- ✅ `【领地争夺】两队同时攻打同一块领地时，后结算方覆盖先结算方结果，导致胜利方未获得归属权`

好标题 = **模块 + 触发条件 + 现象 + 后果**。开发看标题就知道该去翻哪段代码。

### Q6：偶现 BUG 怎么处理？

偶现 BUG 是测试最头疼的，处理逻辑分四步：

1. **详细记录**：环境（机型/系统/网络/画质）、时间点、操作步骤、日志。**截图和录屏一定要留**，后面很难再复现。
2. **尝试多条件复现**：切换设备、切换网络（WiFi/4G/弱网）、改变操作节奏、连续操作多次、切换账号。同一条操作路径多走几次，往往能摸出触发规律。
3. **协助开发加日志**：现象说不清时，主动申请在可疑分支加临时日志，下个版本再抓一次。
4. **标注清楚**：在单子上明确写"偶现，复现率约 X/50"，**不要写成"必现"**，误导开发会浪费大量排查时间。

> 心态上：偶现 BUG 不是"测不出来就不提"。提上去、标清楚复现率，本身就是有价值的输出。

### Q7：什么是回归测试？为什么重要？

修完 BUG 或新增功能后，对**相关区域再次测试**，防止旧问题复发或引入新问题。

实战里的关键问题是"**相关区域怎么划**"：

- 改了领奖逻辑 → 所有发奖入口都要过一遍（活动、邮件、GM 补偿）
- 改了背包结构 → 道具的获得、使用、出售、过期全链路都要测
- 改了战斗数值计算 → 所有涉及伤害的玩法都要抽测

划不出范围时，**直接去问开发改了哪些文件**，比凭感觉猜靠谱得多。

## 三、工具与能力类

### Q8：你熟悉的自动化测试工具有哪些？

按场景分，这样答显得有体系：

| 场景 | 工具 |
|------|------|
| Web 端 | Selenium |
| 手游 / PC 游戏 UI | Airtest、Poco |
| 移动端原生 App | Appium |
| Windows 桌面程序 | pywinauto |
| 接口层 | requests + pytest、Postman |

### Q9：自动化测试在游戏测试中怎么用？

**适合**：重复性高、流程固定的测试 —— 跑图、日常任务、回归测试、登录链路、接口校验。

**不适合**：体验评价、主观判断（打击感爽不爽）、一次性场景、频繁变动的 UI。

> 判断标准很简单：**这件事明天、后天、下个月还要再做一遍吗？** 要的话就值得自动化。

## 四、逻辑与场景题

### Q10：上线前一天发现一个偶现闪退 BUG，怎么办？

这题考的不是技术，是**决策与沟通**：

1. **立刻上报**，同时标注严重等级（崩溃类一般是致命）
2. **提供所有材料**：日志、复现步骤、复现率、影响范围
3. **给出你的判断**：是否建议延期上线 —— 但**决策权不在你**，由项目经理和技术负责人拍板
4. **继续尝试复现**，同时准备好应急方案（热更新回滚、灰度停量）

⚠️ **答这题千万别逞强说"我自己决定上线"**。测试的正确姿态是：**把风险讲清楚，把决策交给该决策的人。**

### Q11：某个怪物掉落率 5%，怎么验证？

杀 1000 次统计掉落次数，看是否落在置信区间内（期望 50 次 ± 合理偏差）。

**关键在于提"小样本不靠谱"这句**：

- 杀 20 次掉了 3 次 → 15%，看起来偏高 → 但样本太小，完全是随机波动
- 杀 1000 次掉 58 次 → 5.8% → 才具备参考意义

如果是高频玩法，用自动化脚本批量跑，比手动杀怪靠谱得多。

### Q12：怎么设计一个新功能的测试用例？

标准四步：

1. **读需求文档**，理解功能逻辑和边界规则（不清的地方**当场问策划**，别猜）
2. 用**等价类划分 + 边界值分析 + 场景法**设计用例
3. 覆盖四类：正常流程 + 异常流程 + 边界条件 + 兼容性
4. **标注优先级**（P0/P1/P2），P0 是核心链路必须过

> **补充一句加分**：写完用例我会找开发/策划过一遍，确认业务规则理解一致——很多漏测其实是"理解错了"，而不是"没想到"。

## 小结

这两类题的共同点是：**答案框架谁都会背，差别全在你举的例子。**

准备面试时，别背文字，去翻自己的工作记录，给每个知识点挂上 1-2 个真实案例。面试官追问"能具体说说吗"的时候，你就稳了。
