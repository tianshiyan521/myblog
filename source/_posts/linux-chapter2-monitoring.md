测试环境"服务起不来""跑着跑着卡了"，第一个要排查的不是代码，是**资源**。

CPU 满了？内存泄漏了？磁盘写满了？**这三条命令能覆盖 80% 的现场问题。**

## 一、top / htop：CPU 和进程

### 基础用法

```bash
top        # 按 q 退出，默认每 3 秒刷新
htop       # 增强版，彩色界面 + 鼠标支持
```

`top` 是 Linux 自带的任务管理器。`htop` 是它的增强版，**更直观，强烈推荐**：

```bash
sudo apt install htop    # Ubuntu/Debian 先装
htop
```

### 实战场景

**① 只看某个用户的进程**

```bash
top -u nginx
```

**② 只看某个进程**

```bash
top -p 12345
```

**③ 按内存排序**

跑起来后按 `Shift + M`，立刻看出哪个进程吃内存。

### 关键指标怎么读

| 指标 | 含义 | 关注点 |
|------|------|--------|
| **load average** | 1/5/15 分钟平均负载 | **超过 CPU 核数就是过载** |
| **%us** | 用户态 CPU 占用 | 应用本身在算 |
| **%sy** | 内核态 CPU 占用 | 系统调用、IO |
| **%wa** | **IO 等待** | **高说明磁盘是瓶颈，不是 CPU** |
| **%id** | 空闲 | 太低说明 CPU 紧张 |

> ⚠️ **`%wa` 高是个特别容易误判的现象**：
> CPU 使用率看起来不高（因为进程都在等磁盘），但系统响应很慢。
>
> **看到 CPU 不高但系统卡，先看 `%wa`。**

### load average 的正确理解

```
load average: 2.50, 3.10, 1.80
```

**关键：要和 CPU 核数对比。**

- 4 核机器，load 3.0 → **75% 负载，正常**
- 2 核机器，load 3.0 → **150% 负载，过载**
- 单核机器，load 8.0 → **严重过载**

```bash
nproc    # 查 CPU 核数
```

> **load 不等于 CPU 使用率**。它统计的是"正在运行 + 等待运行"的进程数，**IO 等待也会推高 load**。

## 二、df / du：磁盘空间

这对命令是排查"**磁盘满了**""**日志爆了**"的黄金搭档：

- `df`（disk free）— 看**文件系统整体**占用
- `du`（disk usage）— 看**指定目录**占用

### df：先看整体

```bash
df -h
```

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   42G  5.3G  89% /
/dev/sdb1       200G  180G   20G  90% /data
```

**`-h` 必须加**，否则显示的是 KB 数，要自己数零。

### du：定位罪魁祸首

```bash
# 看 /var/log 下各子目录的占用
du -h --max-depth=1 /var/log
```

```
12K     /var/log/apt
1.2G    /var/log/mysql
8.5G    /var/log/old_archive    ← 罪魁祸首
```

**`--max-depth=1` 是关键参数** —— 只看一层，避免输出爆炸。

### ★ 排查磁盘满的标准流程

```bash
# ① 确认哪个分区满了
df -h

# ② 从根目录开始，逐层找大目录
du -h --max-depth=1 / | sort -rh | head -10

# ③ 进入最大的目录，继续往下找
cd /var && du -h --max-depth=1 | sort -rh | head -10

# ④ 找到具体的大文件
find /var/log -type f -size +100M -exec ls -lh {} \;
```

> **`sort -rh` 这招很好用** —— `-r` 倒序，`-h` 按人类可读单位排序（否则 1G 会排在 900M 前面）。
>
> 配合 `head -10` 只看前 10 个最大项，**一眼锁定目标**。

### 磁盘满的常见原因

| 原因 | 处理 |
|------|------|
| **日志没有轮转** | 配置 logrotate，或清理旧日志 |
| 临时文件堆积 | 清理 `/tmp`、`/var/tmp` |
| core dump 文件 | 检查进程崩溃、清理 core 文件 |
| 数据库 binlog | 配置过期策略 |

> **⚠️ 在 Windows 上开发的人容易忽略这条**：Windows 一般不会因为日志写满盘，但 Linux 服务器**日志写满盘是最高频的事故之一**。
>
> 表现通常是：**服务莫名起不来、写文件报错、甚至 SSH 都连不上**。

## 三、free：内存

```bash
free -h              # 人类可读
free -h -s 5         # 每 5 秒刷新
watch -n 1 free -h   # 配合 watch 实时刷新
```

### 输出怎么读（重点：别被 available 骗了）

```
              total        used        free      shared  buff/cache   available
Mem:           15Gi        8.2Gi       1.1Gi       0.3Gi       6.2Gi       6.5Gi
Swap:         2.0Gi       512Mi       1.5Gi
```

| 列 | 含义 |
|----|------|
| **total** | 总内存 |
| **used** | 已使用 |
| **free** | **完全空闲**（这个数字通常很小，是正常的） |
| **buff/cache** | 内核缓存（可回收） |
| **available** | **★ 真正可用的内存** |

> **⚠️ 最大的误解：看到 `free` 很小就以为内存不够。**
>
> Linux 的设计哲学是"**空闲的内存是浪费的内存**"——它会把内存用作磁盘缓存来加速 IO。
> 所以 `free` 很小、`buff/cache` 很大，**这是健康的表现，不是问题**。
>
> **真正该看的是 `available`** —— 这个数字已经扣除了不可回收的缓存，代表**新程序真正能拿到的内存**。

### swap 使用情况的判断

- **swap used 很小** → 正常，说明内存够用
- **swap used 持续增长** → ⚠️ **内存压力的信号**，系统在往磁盘上"挤"数据，性能会明显下降
- **大量使用 swap** → 内存严重不足，需要优化或扩容

## 四、三件套的使用顺序

遇到"测试环境有问题"，按这个顺序排查：

```
① df -h        先看磁盘（最容易忽略，也最容易满）
② free -h      看内存和 swap
③ top          看 CPU、负载、具体进程
④ 针对性深入    找到可疑进程后进一步分析
```

> **为什么把 df 放第一？**
>
> 因为磁盘满的**表现极其多样**：服务起不来、接口报错、日志写不进、数据库拒绝写入……
> 这些现象看起来像各种不同的 bug，但根因都是同一个。
>
> **先花 3 秒看 df，能省下后面半小时的排查。**

## 五、小结

| 命令 | 用途 | 关键参数 |
|------|------|---------|
| `top` / `htop` | CPU、进程、负载 | `-u 用户`、`-p PID`、`Shift+M` 按内存排序 |
| `df -h` | 文件系统整体占用 | 查磁盘满的**第一步** |
| `du -h --max-depth=1` | 目录占用 | 配合 `sort -rh \| head` 定位大目录 |
| `free -h` | 内存和 swap | **看 available，不看 free** |

**三个容易误判的点：**

1. **load 高 ≠ CPU 使用率高**（IO 等待也推高 load）
2. **CPU 不高但系统卡** → 看 `%wa`
3. **free 很小不是问题** → 看 available

> **本课要点**：先看磁盘｜load 要跟核数比｜%wa 高是磁盘瓶颈｜available 才是可用内存
