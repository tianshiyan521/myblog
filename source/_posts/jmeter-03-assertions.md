**没有断言的压测只是在"发请求"，不是在"测性能"。**

想象一下：你跑 1000 并发，报告显示错误率 0%、平均响应 200ms，看起来完美。

但这个"成功"的含义只是**请求发出去了、收到了响应**——响应内容是不是对的？字段有没有少？业务码是不是失败？**这些你根本不知道。**

<!-- more -->

## 一、断言解决什么问题

### 采样器成功 ≠ 业务成功

这是 JMeter 里最容易混淆的一点：

| 概念 | 含义 |
|------|------|
| **采样器成功** | HTTP 请求完成，拿到响应（哪怕是 404） |
| **断言成功** | 响应内容符合你的预期 |

**JMeter 默认只看前者。** 所以一个返回 500 的接口，在报告里可能显示"成功"——因为请求本身完成了。

⚠️ **极端情况**：被测服务挂了，返回一个静态错误页，HTTP 200，内容里写着"系统维护中"。**没有断言的话，你的报告是全绿的。**

### 断言在哪里生效

断言挂在采样器（或其父级）下面，**只对所在作用域内的采样器生效**。

可以在 **Test Plan / Thread Group / Sampler** 三个层级放置，作用域逐级收窄。

## 二、5 种断言类型详解

### 1. 响应断言（Response Assertion）

**适用场景**：检查响应码、响应消息、响应体、响应头、请求 URL 等**文本内容**。

| 配置项 | 含义 | 常用值 |
|--------|------|--------|
| `test_field` | 检查对象 | `response_code` / `response_message` / `response_data` / `response_headers` |
| `test_type` | 匹配方式 | `Matches` / `Contains` / `Not` / `Equals` / `Substring` |
| `assume_success` | 忽略状态 | `true` 表示 4xx/5xx 先强制视为成功，再执行断言 |

> 💡 **`Ignore status` 的用处**：测试"接口该返回 404"这类用例时，不开这个选项，JMeter 会因为 404 直接判定请求失败，断言根本没机会执行。

⚠️ **JMeter 5.6.3 的常量值容易搞混**：`EQUALS=8`、`CONTAINS=2`、`SUBSTRING=16`，**不是**直观的 1/2/4/8。手工改 XML 时特别容易写错。

### 2. JSON 断言（JSON Path Assertion）

**适用场景**：RESTful 接口返回 JSON，需要校验**具体字段值**。

```
JSON_PATH       →  $.url、$.data[0].id
EXPECTED_VALUE  →  期望值
ISREGEX         →  是否把期望值当正则
JSONVALIDATION  →  是否启用校验
EXPECT_NULL     →  是否期望值为 null
INVERT          →  反转结果（不匹配才通过）
```

> ⚠️ **踩坑**：`ISREGEX=true` 时是**完整匹配**（等价于 `String.matches()`）。
> 想匹配 "包含 httpbin.org"，写 `httpbin.org` 会**失败**，必须写成 `.*httpbin\.org.*`。
>
> **这个坑很隐蔽**——断言失败但看表达式觉得"没问题"，实际上差的是两端的 `.*`。

### 3. 持续时间断言（Duration Assertion）

**适用场景**：对响应时间做**硬性上限**约束。

> "登录接口必须在 1 秒内返回。"

超过阈值就判定失败。**这条断言把性能要求变成了可执行的用例**——这是性能测试和功能测试结合得最好的地方。

### 4. 大小断言（Size Assertion）

**适用场景**：校验响应体大小。

- 响应体突然变小 → 可能返回了错误信息而不是数据
- 响应体突然变大 → 可能返回了异常堆栈

**这是个便宜的兜底断言**，能抓住不少内容异常的情况。

### 5. BeanShell 断言（BeanShell Assertion）

**适用场景**：前面几种都表达不了的复杂逻辑，用 Java/脚本代码写。

**能用内置断言就别用 BeanShell** —— 可读性差、执行慢、别人难以维护。

## 三、断言设计的一个原则

**断言要"恰到好处"，不是越多越好。**

| 断言过多 | 断言过少 |
|---------|---------|
| 一个字段变动就全红，维护成本爆炸 | 返回错误页也显示通过 |
| 干扰真正的问题定位 | 漏掉内容层面的失败 |

**推荐组合**（按性价比排序）：

1. **响应码断言**（最基础，成本最低）
2. **业务码断言**（JSON 断言 `$.code == 0`）
3. **关键字段断言**（JSON 断言校验 `$.data.token` 非空）
4. **持续时间断言**（把性能要求固化下来）

> **特别提醒游戏接口**：很多游戏网关的 HTTP 状态码**永远是 200**，真实成败藏在响应体里。
> 这种情况**必须**加业务码断言，只看响应码等于没测。

## 四、小结

| 要点 | 内容 |
|------|------|
| **核心认知** | **采样器成功 ≠ 业务成功** |
| 5 种断言 | 响应 / JSON / 持续时间 / 大小 / BeanShell |
| 常用组合 | 响应码 + 业务码 + 关键字段 + 持续时间 |
| 踩坑 | JSON 断言 `ISREGEX` 是**完整匹配**，要加 `.*` |
| 技巧 | `Ignore status` 用来测"该返回 4xx"的用例 |
| 原则 | 恰到好处，不是越多越好 |

> **本课要点**：没断言的压测只是发请求｜采样器成功 ≠ 业务成功｜JSON 断言是完整匹配
