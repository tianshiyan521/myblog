第 2 章讲 BUG 管理时，末尾只留了一行流程：

```
需求分析 → 用例设计 → 用例评审 → 执行测试 → 提交BUG → 回归验证 → 关闭BUG
```

这行流程看着简单，但被追问细节时很多人会卡住：

- 缺陷被**拒绝**了怎么办？
- **谁有权关闭**一个缺陷？
- 开发说修好了，但我复测还是有问题，这算**新缺陷**还是**原缺陷**？
- 那些确认是 BUG 但**这版本不修**的，去哪了？

这篇把这条线单独展开。

<!-- more -->

## 一、标准六态流转

```
新建 → 已分配 → 处理中 → 已修复 → 待验证 → 已关闭
                    ↑                    │
                    └──── Reopen ────────┘
```

| 状态 | 英文 | 谁在操作 | 这个阶段要做什么 |
|---|---|---|---|
| **新建** | New | 测试 | 提单：复现步骤、期望/实际结果、版本号、日志录屏 |
| **已分配** | Assigned | 测试组长 / 开发负责人 | 定性（是不是缺陷）+ 指派给具体开发 |
| **处理中** | Open | 开发 | 定位根因 + 修复；需要信息时找测试补 |
| **已修复** | Fixed | 开发 | 代码提交，等待版本出包 |
| **待验证** | Pending Retest | 测试 | 复测原路径 + **回归关联功能** |
| **已关闭** | Closed | 测试 | 复测通过后关闭 |

### 这里有三条容易被忽略的规则

**① 只有测试有权关闭缺陷**

开发最多把状态推到「已修复」。代码提交 ≠ 问题解决——他可能只改了表象，也可能引入了新问题。**关闭这个动作必须由验证方做**。

如果你的团队是开发自己关单，那这个流程已经失效了。

**② 状态不能跳**

从「新建」直接跳到「已关闭」，意味着**没有任何人验证过**。这种情况在赶版本时特别容易发生，也是上线后漏 BUG 的主要来源。

**③ Reopen 不是失败，是流程正常运转**

回退箭头是这条链路上最关键的一环。判断该不该 Reopen，看这三条：

| 判据 | 具体表现 | 数据化表达 |
|---|---|---|
| **修得不彻底** | 原 10 次触发 5 次，改完 10 次触发 1 次 | 给出修复前后的触发率对比 |
| **引发新问题** | 原功能好了，旁边功能挂了 | 附上回归时发现的新现象 |
| **只修了表象** | 界面数字对了，库里存的还是错的 | 附上查库结果 |

> ⚠️ 第一条最容易扯皮。开发会说"这是偶现，不是没修好"。**你手上要有前后对比的数据**——"修复前 100 次触发 47 次，修复后 100 次触发 9 次"，这种数据一贴出来，就没有讨论空间了。

## 二、三个分支终态

主线之外，缺陷还有三个去处。面试问到要能完整说出来：

| 分支状态 | 触发场景 | 谁有权定 | 测试该做什么 |
|---|---|---|---|
| **拒绝 Rejected** | 不是缺陷 / 设计如此 / 无法复现 | 策划或开发 | 写申诉理由 + 附证据；测试有**申诉权** |
| **延期 Deferred** | 确认是缺陷，但本版本不修 | 策划 + 项目负责人 | 记进遗留清单，跟进到下个版本 |
| **重复 Duplicate** | 已有人提过同类问题 | 测试自己合并 | 合并到原单，补充自己发现的新复现条件 |

### 「无法复现」不是拒绝理由

游戏项目里最常被卡的就是这一条。玩家反馈的偶现问题，开发一句"我这边复现不了"就想关掉。

**正确做法是挂起观察，而不是拒绝**：

1. 补齐三件套 —— **客户端版本号 + 完整日志 + 录屏**
2. 摸出**触发概率** —— 10 次操作触发几次，这是最有力的证据
3. 缩小**触发条件** —— 特定机型？特定网络？特定玩法组合？打完一场之后？
4. 标记为"偶现"挂起，等下次出现时补证据

只有当你**能稳定证明它是设计如此**时，才走拒绝。

## 三、严重程度 ≠ 优先级

这是缺陷管理里最容易被追问的一点，也是最能体现判断力的地方。

| | 严重程度 Severity | 优先级 Priority |
|---|---|---|
| 衡量什么 | 缺陷本身的破坏力 | 修复的紧迫度 |
| 谁说了算 | **测试**（客观） | **策划 / 项目负责人**（主观） |
| 依据 | 影响范围、可玩性、数据安全 | 版本节奏、玩家感知、修复成本 |

**两者不成正比**，这是核心结论。用四个象限看：

| 象限 | 典型场景 | 处理方式 |
|---|---|---|
| 高严重 + 高优先 | 崩溃、卡死、充值扣钱但道具未到账 | **立即修复** |
| 低严重 + 高优先 | 新手指引文案写错、首屏错别字 | **本版本必修** |
| 高严重 + 低优先 | 隐藏副本必崩、特定冷门机型闪退 | **排期修复** |
| 低严重 + 低优先 | 边缘文案、异常分辨率下轻微错位 | **延期 / 挂起** |

举个真实感的例子：

> 某个隐藏副本里，Boss 二阶段必定触发闪退——这是**严重程度高**的问题。但那个副本只有 0.1% 的玩家会进，改它要动战斗核心逻辑，风险比收益大。所以它的**优先级低**，排到下个版本修。
>
> 而新手指引里"攻击"按钮的文案被写成了别的词——**严重程度低**（只是个错别字），但每个新玩家第一眼看到的就是它，直接影响首日留存。所以它**优先级高**，当天就改。

**面试时如果只答"严重的先修"，就掉坑里了。** 要主动说出"这两个字段是分开的，各自由谁定"。

## 四、游戏项目里的流程变形

标准流程是规范，但游戏研发的实际节奏会让它发生变形。能说清楚这些变形，说明你不是在背书。

**① 封版裁决**

版本封版时，所有未关闭的缺陷会被逐条裁决：

```
阻塞发布（Blocker） → 必须修完才能出包
本版本必修          → 排进封版前的最后一批
顺延下版本          → 状态改为「延期」，记入遗留清单
长期挂起            → 影响极小或修复成本过高
```

这也是为什么会有那么多「延期」状态的缺陷——**不是没人管，是被裁决过**。

**② 热修跳级**

线上出阻塞性问题时，会走热修流程，跳过完整的「开发 → 出包 → 回归」链路。但这种情况下，**后补缺陷单留痕的动作不能省**——否则下次出问题，没有历史记录可查。

**③ 偶现问题挂起观察**

前面说过，不直接拒绝，而是挂起 + 持续监控。

**④ 缺陷的"寿命"通常只有一个版本周期**

版本节奏快的项目（双周版、周版），一个缺陷从 New 到 Closed 通常在 1-2 个版本内解决。超过 3 个版本还挂着的，基本可以认为**它不会被修了**，要主动从遗留清单里清出去。

## 五、工具落地：状态名对照

不同缺陷管理平台的状态名不一样，但语义是通的。面试时能对照着说，会显得你真用过：

| 标准状态 | 常见工具里的叫法 |
|---|---|
| New | 新建 / 待确认 |
| Assigned | 已分配 / 待处理 |
| Open | 处理中 / 开发已确认 |
| Fixed | 已解决 / 已修复 |
| Pending Retest | 待验证 / 待回归 |
| Closed | 已关闭 / 已验证 |
| Rejected | 已拒绝 / 非缺陷 / 不予处理 |
| Deferred | 已延期 / 挂起 / 暂不修复 |

**每个缺陷单必须能被单独检索和统计**，否则谈不上管理。常用的几个字段：

- **状态** —— 流转到哪了
- **处理人** —— 现在卡在谁手上（这个字段空白最危险）
- **严重等级 + 优先级** —— 决定修复顺序
- **关联需求 / 关联用例** —— 反查影响范围
- **发现版本 + 修复版本** —— 用来算缺陷寿命

## 六、进阶：两个能体现水平的指标

**缺陷生命周期时长（Cycle Time）**

从「新建」到「已关闭」的平均耗时。这个指标卡在**「已分配 → 处理中」**这段最容易失控——缺陷提了没人认领，就在那里"躺尸"。

所以作为测试，要主动盯这个环节：**提完单不等于交出去**，要确认有人接手、有人认领。

**缺陷逃逸率（Defect Escape Rate）**

```
缺陷逃逸率 = 上线后发现的问题数 / (测试阶段发现 + 上线后发现的 总问题数)
```

这个指标衡量的是**测试有没有拦住问题**，而不是"测试提了多少 BUG"。

> 顺带说一句：**提 BUG 数量从来不是考核指标**。同一类问题提 20 个单，和提 1 个单 + 一个可复用的检查点，后者价值高得多。

## 七、面试怎么答（三层结构）

**框架层** —— 先给完整链路：

> 新建 → 已分配 → 处理中 → 已修复 → 待验证 → 已关闭，中间有 Reopen 回退，旁路有拒绝 / 延期 / 重复三个分支。

**项目层** —— 落到自己做的事：

> 我最关注两个卡点：一是「已分配」到「处理中」这段最容易躺尸，我会主动盯处理人字段有没有空；二是「待验证」环节必须做回归，不能只验原路径——只验原路径最容易漏掉"修复引发新问题"。

**局限层** —— 主动说流程的变形：

> 标准流程在实际项目里是有变形的。版本节奏快，封版时会有一次裁决，确认的缺陷可能被强制定为延期；线上阻塞性问题走热修，会跳过完整流程，但补单留痕不能省。所以流程是规范，执行要看版本阶段。

---

## 小结

缺陷生命周期表面是"状态怎么流转"，实际考的是三件事：

1. **职责边界** —— 谁能关单、谁能拒绝、测试有申诉权吗
2. **证据意识** —— 说"没修好"要拿前后数据，说"无法复现"要拿版本日志录屏
3. **判断力** —— 严重程度和优先级分开看，不是"严重的先修"

流程本身不难，**难的是每个环节你都能说清楚"凭什么"**。
