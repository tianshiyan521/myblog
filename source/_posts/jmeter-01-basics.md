性能测试是测试工程师的能力分水岭之一。功能测试能靠细心补，但性能测试**必须靠工具 + 方法**。

JMeter 是 Apache 开源的纯 Java 性能测试工具，也是目前上手成本最低的一个。

这个系列按 7 天的学习过程整理成文。

<!-- more -->

## 一、JMeter 能做什么

| 能力 | 说明 |
|------|------|
| **接口性能测试** | 模拟多用户并发，测吞吐量（QPS/TPS）、响应时间 |
| **负载测试** | 逐步加压，找到系统瓶颈 |
| **压力测试** | 极限并发，测系统崩溃点 |
| **功能测试** | 也能做接口自动化（但不如 Postman/requests 方便） |

> **给测试的一句话**：JMeter 的价值不在"能发请求"，而在于**能同时发 1000 个请求，并把结果统计出来**。

---

## 二、核心架构（5 层）

```
Test Plan（测试计划）
  └── Thread Group（线程组 = 虚拟用户）
        ├── Config Element（配置元件：HTTP默认值、CSV、Header Manager）
        ├── Sampler（采样器：HTTP Request、JDBC、TCP...）
        ├── Timer（定时器：固定定时、随机定时、吞吐量定时器）
        ├── Assertion（断言：响应断言、JSON断言、持续时间断言）
        ├── Post Processor（后置处理器：正则提取器、JSON提取器）
        └── Listener（监听器：查看结果树、聚合报告、汇总报告）
```

**三个关键理解：**

1. **Thread Group = 并发用户数**。JMeter 里每个线程就是一个独立用户
2. **Sampler = 真正发请求的东西**。其他元件都是围绕它服务的
3. **Listener = 收集结果的地方**。⚠️ **不要在 GUI 模式下开太多监听器**，它们很吃内存，会拖慢测试本身

---

## 三、★ 最重要的一条规则：GUI 写脚本，CLI 跑压测

| 模式 | 用途 | 命令 |
|------|------|------|
| **GUI** | 编写 / 调试脚本 | `jmeter.bat` |
| **CLI** | 执行性能测试 | `jmeter -n -t xxx.jmx -l result.jtl -e -o report/` |

**为什么不能用 GUI 跑压测？**

GUI 本身要渲染界面、绘制图表，这些开销和被测系统抢 CPU、抢内存。**在 GUI 里跑出来的数据是不准的**——你测的可能不是服务端的极限，而是你自己电脑的极限。

> 这条规则我一开始不以为然，直到有一次在 GUI 里跑 50 并发，本机 CPU 直接拉满、界面卡住。换成 CLI 跑，同样的脚本轻松跑到 200 并发。
>
> **工具自己成了瓶颈**，这是性能测试里最讽刺的失误。

### CLI 参数说明

```bash
jmeter -n \                          # 非 GUI 模式
       -t jmeter_day1.jmx \          # 测试计划文件
       -l day1_result.jtl \          # 结果文件（JTL）
       -e -o day1_report/            # 生成 HTML 报告到目录
```

## 四、第一个测试计划

```
Test Plan: HTTP 基础请求入门
├── 用户定义变量: BASE_URL=httpbin.org, TEST_USER=jmeter_learner
├── Thread Group: 基础并发线程组
│   ├── 线程数: 5
│   ├── Ramp-Up: 2 秒
│   ├── 循环次数: 2
│   └── 总请求: 5 × 2 × 3 = 30 次
├── HTTP Request Defaults (base URL = httpbin.org)
├── HTTP Header Manager (Accept / User-Agent)
├── 【采样器1】GET /get — 基础 GET
├── 【采样器2】GET /get?name=xxx — 带参数 GET
├── 【采样器3】POST /post — JSON 提交
├── 查看结果树 / 聚合报告 / 汇总报告
```

### 关键参数

| 参数 | 含义 | 本次值 |
|------|------|--------|
| **线程数** | 并发用户数 | 5 |
| **Ramp-Up** | 启动间隔（秒） | 2s（每 0.4s 启动一个用户） |
| **循环次数** | 每个用户执行几遍 | 2 |
| **总采样数** | 线程数 × 循环 × 采样器数 | 5 × 2 × 3 = **30** |

### Ramp-Up 是很多人搞混的参数

**它不是一个"等待时间"，而是"爬坡时间"。**

- 线程数 5，Ramp-Up 2s → **每 0.4 秒启动 1 个用户**，2 秒内启动完
- 线程数 100，Ramp-Up 1s → **每 0.01 秒启动 1 个用户**

⚠️ **Ramp-Up 设太小会出现"瞬时冲击"**：100 个线程 1 秒内全起来，和真实用户逐渐进入的场景不符。

**经验值**：Ramp-Up ≈ 线程数 × 0.1~0.5 秒。比如 100 线程，Ramp-Up 设 10~50 秒更接近真实。

### 变量引用

JMeter 用 `${}` 引用变量，和 Shell 一样：

```
${BASE_URL}   →  httpbin.org
${TEST_USER}  →  jmeter_learner
```

## 五、聚合报告：怎么看性能数据

| 字段 | 含义 | 判断标准 |
|------|------|---------|
| **Samples** | 请求次数 | — |
| **Average** | 平均响应时间（ms） | 越小越好，< 500ms 算好 |
| **Median** | 中位数响应时间 | **比 Average 更能反映真实体验** |
| **90% Line** | 90% 请求的响应时间 | **性能 SLA 通常看这个** |
| **95% Line** | 95% 请求的响应时间 | — |
| **99% Line** | 99% 请求的响应时间 | — |
| **Min / Max** | 最小 / 最大响应时间 | **Max 很大说明有抖动** |
| **Error%** | 错误率 | **必须 0%** |
| **Throughput** | 吞吐量（请求/秒） | 越大越好 |
| **Received / Sent KB/sec** | 收发速率 | — |

### 为什么看 90% Line 而不是 Average

举例：100 个请求里

- 95 个请求响应 100ms
- 5 个请求响应 **8000ms**

**Average = (95×100 + 5×8000) / 100 = 495ms** —— 看起来还行

但其实**有 5% 的用户等了 8 秒**。他们的体验是灾难，而平均值把这个灾难"平均掉"了。

**这就是为什么性能 SLA 通常写"90% 请求响应时间 < 500ms"而不是"平均响应时间 < 500ms"。**

> **记住这条**：**平均值会骗人，分位数不会。**

## 六、Day 1 结论

| 要点 | 内容 |
|------|------|
| 架构 | Test Plan > Thread Group > Sampler > Listener |
| 线程组 | = 虚拟用户，控制并发 |
| 元件复用 | HTTP Request Defaults 统一配置，避免重复 |
| 变量 | `${}` 引用 |
| **模式** | **GUI 写脚本，CLI 跑压测** |
| 看报告 | Average、**90% Line**、Error%、Throughput |

---
