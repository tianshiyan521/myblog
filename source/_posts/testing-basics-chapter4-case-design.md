"你会设计用例吗？"——面试官问这句时，想听的不是"我会等价类边界值"，而是**你能不能在具体功能上把它用出来**。

这篇把六大方法论拆开讲，每个都配游戏场景的实例。

<!-- more -->

## 为什么需要方法论

不用方法的后果很具体：**想到哪测到哪，测完心里没底。**

用过方法之后，你能回答两个关键问题：

- 这个功能**我测完了吗**？（覆盖度可控）
- 这个版本**我该优先测什么**？（优先级有依据）

这就是"能评审"和"不能评审"的区别。

---

## 一、等价类划分

**核心思路**：把输入数据分成若干等价类，每类中任取一个代表值即可。

```
示例：注册时填写年龄（1-120 岁）

有效等价类： 1 ≤ age ≤ 120
无效等价类： age < 1（0、负数）
            age > 120（121、9999）
            非数字（"abc"、空值、null）
```

**三条实战要点：**

1. **不只分有效/无效，还要考虑数据类型**：数字、字符串、特殊字符、布尔值，每一类都要有代表
2. **一条用例可以覆盖多个有效等价类**（压缩用例数量）
3. **一条用例只覆盖一个无效等价类** —— 否则程序在第一个错误处就返回了，后面的错误被掩盖，你以为测了其实没测

> 第 3 条是新人最常犯的错。**无效等价类必须一个一个来。**

**游戏场景**：领奖接口的 `rewardId` 参数 —— 有效类（1/2/3 三个存在的礼包）、无效类（不存在的 id、0、负数、超长数字、字符串）。

## 二、边界值分析

**核心思路**：错误往往聚集在边界，别只测"典型值"。

```
经典边界口诀：
  上点 → 边界值本身（120）
  离点 → 边界 ±1（119、121）
  内点 → 边界内的典型值（60）

年龄 1-120，测：0, 1, 2, 60, 119, 120, 121   ← 7 个值覆盖所有边界
```

⚠️ **空值、空字符串、null 也是边界！** 很多人会漏掉。

**游戏里的日常场景：**

| 功能 | 边界测什么 |
|------|-----------|
| 背包容量上限 | 满、满+1、满-1 |
| 充值金额 | 0.01、0、负数、超大值 |
| 排行榜名次 | 第 1 名、第 100 名（上限）、第 0 名（不存在） |
| 等级门槛 | 门槛-1、门槛、门槛+1 |

### ⚠️ 一个真实的边界 bug

我实测过一个假服务端，规则是"**10 级可以领王者礼包**"，代码却是：

```python
if u_["level"] <= cfg["need_level"]:   # ← 问题在这
    return self._err(50002, f"王者礼包需要 10 级，你当前 {u_['level']} 级")
```

**少了一个等号。** 于是 10 级玩家收到的报错是：

> "王者礼包需要 10 级，你当前 10 级"

需要 10 级，我是 10 级，凭什么不让我领？**这句报错本身就自相矛盾。**

这就是最经典的边界值缺陷。手动测试时的自然路径是：

- 试 5 级 → 领不了 ✅ 符合预期
- 试 20 级 → 能领 ✅ 符合预期
- 然后觉得"没问题"了

但"**正好 10 级**"这个点，**得特意去构造才会碰到**。而开发写错的，往往恰好就是这一个点。

> **边界上的人最少，出的事最多。**

## 三、因果图法

**适用场景**：多个输入条件之间有逻辑组合关系。

```
示例：VIP 特权判定

条件（因）：
  C1: 是 VIP    C2: 等级 ≥ 50    C3: 充值 ≥ 1000

动作（果）：
  A1: 可进入特权副本    A2: 可领取每日宝箱    A3: 出战位 +1

用 AND / OR / NOT 画出逻辑关系后，逐组合验证：
  (C1=Y, C2=Y, C3=Y) → A1 + A2 + A3 全触发
  (C1=Y, C2=N, C3=N) → 仅 A2（VIP 基础权利）
  (C1=N, C2=Y, C3=Y) → 0 触发（非 VIP 一律不行）
```

**为什么需要它**：3 个条件就是 8 种组合，靠"想到哪测哪"必然漏。画出来之后，漏没漏一眼可见。

**游戏里的典型场景**：活动参与条件、特权判定、多条件筛选项、折扣叠加规则。

## 四、错误推测法

**不是系统方法，是经验直觉。** 老测试的第六感来自踩过的坑。

常见清单：

- 空输入、超长输入
- 并发操作（同时点两个按钮）
- 异常中断（支付中断网、战斗中断电、切后台）
- 边界 ±1
- 特殊字符（emoji、SQL 注入字符、零宽字符）
- 重复提交、快速连点

⚠️ **但要注意分寸**：如果一份用例里错误推测占比过高（比如超过 30%），说明**用例主要靠个人经验，不可评审也不可传承**。这时候需要把那些"凭直觉"的点**转化成有方法支撑的用例**。

> **判断标准**：你能向别人解释"为什么测这一条"吗？能，就是方法；不能，就是直觉。

## 五、白盒测试方法（了解即可）

游戏测试以黑盒为主，但白盒的覆盖度分级值得知道：

| 方法 | 强度 | 说明 |
|------|------|------|
| 语句覆盖 | 最弱 | 每个语句至少执行一次 |
| 判定覆盖 | 较强 | 每个判断的 True/False 分支都走到 |
| 条件覆盖 | 更强 | 每个条件的取值组合都覆盖 |
| 路径覆盖 | 最强 | 每条执行路径都走一遍（通常不现实） |

**语句覆盖的陷阱**：

```python
if (a > 0 and b > 0):
    x = 1
else:
    x = 2
```

只测 `(a=1, b=1)` 和 `(a=-1, b=-1)`，语句覆盖率看起来 100%。但 `a>0 且 b≤0` 的**短路情况完全没测到**——这就是假覆盖。

**实践建议**：

- 小函数 / 核心模块 → 追求条件覆盖
- 常规业务 → 判定覆盖 + 关键边界
- 不必强求 100% 路径覆盖（成本不成比例）

## 六、场景法

**核心思路**：按用户的真实使用路径串联功能，验证端到端的业务流程。

场景法经常被低估，但它能抓住**单接口测试抓不到的问题**——接口之间的数据传递、状态依赖。

**游戏场景**：一整套"新手 7 日"流程

```
注册 → 创建角色 → 过新手引导 → 领新手礼包 → 打第一场战斗 
→ 升级 → 解锁功能 → 领七日奖励 → 次日登录看是否接续
```

这类串联测试最容易暴露：状态未持久化、跨天逻辑错乱、前后置条件依赖问题。

## 七、组合使用：一个接口怎么测

以"领取礼包"接口为例，把方法组合起来：

| 方法 | 产出用例 |
|------|---------|
| **正常流程** | rewardId=1，等级足够 → 领取成功，金币增加 |
| **等价类** | rewardId 不存在的值、类型错误的值 |
| **边界值** | 等级 = 门槛-1、门槛、门槛+1 |
| **业务逻辑** | 重复领取（幂等）、并发领取、前置任务未完成 |
| **异常容错** | token 失效、超时重试、参数缺失 |
| **场景法** | 从"打开活动页 → 点击领取 → 查看背包"完整走一遍 |

**六类合起来，才叫"测完了"。**

---

## 小结

| 方法 | 什么时候用 |
|------|-----------|
| 等价类划分 | 输入取值范围大，需要压缩用例数 |
| 边界值分析 | 有数值门槛、容量上限、时间边界 |
| 因果图法 | 多个条件有逻辑组合（权限、活动规则） |
| 错误推测法 | 补充经验盲区（但占比别太高） |
| 场景法 | 验证端到端流程与状态依赖 |
| 白盒覆盖 | 评估代码覆盖质量（了解即可） |

**最后一句：方法不是用来背的，是用来在评审会上说服别人的。**

当你说"这条用例覆盖了等级门槛的上点、离点、内点"时，没人能反驳你漏测；当你说"我觉得这里可能有问题"时，别人只能回你"再看看"。
