## 三个最值得先掌握的点

### ① 用例设计方法不是用来背的

很多人的"用例设计"其实是"凭经验想到哪测到哪"。这样做的后果是：

- 说不清**测完了没有**（覆盖度不可控）
- 说不清**该优先测什么**（没有依据）
- 别人**没法评审**你的用例（因为他也不知道你漏没漏）

**方法的价值就在于让这三件事变得可回答。**

其中**边界值分析**的投入产出比最高。因为我实测遇到过一个真实的边界缺陷：

```python
# 规则：10 级可以领礼包
if u["level"] <= cfg["need_level"]:   # ← 少了一个等号
    return err(50002, "王者礼包需要 10 级，你当前 10 级")
```

结果 10 级玩家收到的报错是"需要 10 级，你当前 10 级"——**报错本身就自相矛盾**。

手动测试的自然路径是"试 5 级不行、试 20 级可以"，然后觉得没问题了。**"正好 10 级"这个点得特意去构造才会碰到。**

> **边界上的人最少，出的事最多。**

### ② HTTP 200 ≠ 用例通过

这条听起来简单，但踩过的人非常多。

很多游戏网关的 **HTTP 状态码永远是 200**，真实成败藏在响应体里：

```json
// HTTP 200，但业务失败了
{ "code": 50002, "msg": "等级不足", "data": null }
```

所以：

```python
assert r.status_code == 200        # ❌ 自欺欺人
assert r.json()["code"] == 0       # ✅ 有效断言
```

**完整校验应该分四层**：

| 层 | 验什么 |
|---|--------|
| 协议层 | HTTP 状态码 |
| 业务层 | 响应体业务码 |
| 数据层 | 字段值与格式 |
| **副作用层** | **数据库/下游真的变了** |

**第四层最容易被跳过** —— 接口返回成功但数据没落库，是最典型的"看着没问题其实是事故"。

### ③ 重试逻辑必须建立在"已证明是瞬时抖动"之上

这条是踩坑换来的，写在别处很少有人讲：

我写过一个"聪明"的重试逻辑，把 **499 也当成限流**去退避重试。结果某个用例判定随机飘，查了半天。

真相是：**499 是协议层的确定性响应，跟频率完全无关。**

证据：
- 同一伪造 token，间隔 1.5s 连打 8 次 → **8 次全是 499**
- 反向验证：40 次错误密码、30 次高频正确登录 → **一次限流都没触发**

**教训**：看到错误码就重试，等于**用一个错误假设掩盖了真实的协议行为**。只对 502/503/504（真正的服务端故障）重试才安全。

> **通用原则**：任何重试逻辑的前提，是先证明"这是瞬时抖动"。验证方法就是**固定输入 + 拉大间隔重复打**。
