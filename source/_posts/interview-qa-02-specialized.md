## 一、网络协议：TCP 与 UDP 怎么选

### Q1：在线游戏中，TCP 和 UDP 有什么区别？各自用在什么场景？

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 保证送达、保证顺序 | 不保证送达与顺序 |
| 速度 | 慢（有确认与重传开销） | 快 |
| 适用 | 数据不能丢的场景 | 延迟敏感的场景 |

**在 MMO/SLG 里的实际分工：**

| 场景 | 协议 | 原因 |
|------|------|------|
| 登录、支付、聊天、背包 | TCP | 数据丢了就是事故，宁可慢 |
| 角色移动、实时战斗同步 | UDP | 位置更新频率高，丢一帧不致命，下一帧就补上了 |
| 战斗过程 vs 战斗结算 | 混合 | 过程走 UDP 抢低延迟，结算走 TCP 保数据准确 |

**如果让你测领地争夺的网络同步，关注这些：**

- **不同延迟下的一致性**：100ms / 300ms / 500ms 延迟下，双方看到的战斗结果是否一致
- **断线重连**：战斗中掉线，重连后地位、血量、Buff 状态是否正确恢复
- **丢包表现**：10% / 30% 丢包时，技能是否出现"放出来了但没生效"或"放两次"
- **弱网切换**：WiFi 与 4G 来回切，是否出现卡死或状态错乱

## 二、性能问题排查：一套可复用的思路

### Q2：玩家反馈"打领地争夺战时画面特别卡"，你如何系统性排查？

这题是**专项测试里的高频题**。答得好不好，看你有没有方法论。

**第一步：先分清"卡"是哪一种**

> ⚠️ 这是最容易被跳过、但最关键的一步。

- **帧率低** → 画面不流畅、掉帧、一顿一顿
- **延迟高** → 操作后半天才有反应、角色瞬移、回弹

两者排查方向完全不同。**分不清就开查，等于白查。**

**第二步：收集基础信息**

设备型号、系统版本、画质设置、战斗参与人数、网络环境。先判断是普遍问题还是特定机型问题。

**第三步：本地复现并拿数据**

用相同或更低配置设备复现。用 PerfDog / GPU Profiler 监测帧率、CPU、内存、GPU 占用——**要拿到具体数字，不能只说"确实卡"**。

**第四步：单变量定位**

| 变量 | 怎么测 | 关注什么 |
|------|--------|---------|
| 人数 | 10 人 vs 30 人 vs 50 人同屏 | 帧率随人数下降的斜率 |
| 特效 | 关闭技能特效/粒子后复测 | 帧率是否明显回升 |
| 资源 | 连续打多场后监测内存 | 内存是否持续上涨（泄漏特征） |
| 画质 | 不同画质档位对比 | 差异是否合理 |

**第五步：排除网络干扰**

延迟高的表现是"瞬移/回弹"，帧率低是"画面不连贯"。**能区分才能精准甩锅给谁。**

**第六步：输出报告**

给出具体数据（最低帧率、平均帧率、卡顿频率）+ 优化建议（减少同屏特效、LOD 优化、对象池复用），并明确标注复现环境。

## 三、逻辑场景题：数据不一致类

### Q3：多名玩家反馈"打赢了战斗却没获得领地所有权"，怎么分析？

这类"**明明成功了却没生效**"的题，是游戏测试面试的经典类型。核心思路：**沿着数据链路从后往前找断点。**

**可能原因（按概率排序）：**

1. **并发竞争（最常见）**：两支队伍同时攻打同一块领地，A 队先打完但 B 队结算更晚写入，覆盖了 A 队的结果 → 并发写入数据覆盖
2. **前后端判定不一致**：客户端显示胜利，但服务端某关键技能的伤害计算不同，判定为失败
3. **隐藏前置条件未满足**：有公会等级、参战人数下限等条件，赢了战斗但不满足占领规则
4. **时序边界**：战斗刚好在争夺截止时间过后结算，结算被丢弃
5. **展示层延迟**：归属已更新，但客户端缓存了旧数据，玩家看到的是旧状态

**测试设计：**

- **并发场景**：模拟两队同时进攻同一领地，验证服务端是否有锁机制、最终结果是否唯一
- **前后端一致性**：对比客户端战斗日志与服务端战斗日志，逐项检查伤害/血量/胜负判定
- **规则验证**：逐条核对占领条件，确认每条在 UI 上都有明确提示（游戏里"规则没写清楚"和"功能有 bug"是两回事，都要提）
- **时间边界**：截止前 1 秒发起战斗、截止前 0.1 秒结束战斗，验证结算行为
- **刷新验证**：战斗结束后强制刷新/重进游戏，确认归属显示正确

> **加分点**：这类问题最后一定要问一句"**这块的写入有没有加锁/幂等？**"——把问题定位到具体机制，比罗列现象高一个层次。

### Q4：玩家反馈"赢了 5 场但排行榜没显示排名"，怎么排查？

排行榜是**数据不一致的高发模块**，核心风险在「数据源 → 计算 → 展示」三层断链。

**先列可能原因：**

| # | 原因 | 验证方式 |
|---|------|---------|
| 1 | 战斗结果未成功上报（弱网/超时） | 查服务端是否有该场次记录 |
| 2 | 排行榜是定时快照，未到刷新时间 | 等一个刷新周期再看 |
| 3 | 有最低场次/积分门槛，被过滤 | 核对门槛规则 |
| 4 | 跨服数据未合并，看错服了 | 确认玩家所在服与榜所属服 |
| 5 | 客户端缓存了旧榜单数据 | 清缓存/重进游戏 |

**排行榜专项测试方案（六维度）：**

| 维度 | 测试要点 |
|------|---------|
| **数据准确性** | 榜单分数与实际战绩是否一致（胜场、积分逐项核对） |
| **排序正确性** | 同分时的排序规则明确吗？分数变化后是实时更新还是延迟 |
| **并发安全** | 多人同时结算时榜单是否错乱（可用 JMeter 压） |
| **刷新机制** | 实时 vs 定时快照，间隔是否合理，玩家等待是否可接受 |
| **跨服/分区** | 合服后 Top100 是否正确合并、有无重复 |
| **展示与边界** | 空榜、自己不在榜、榜尾、翻页、赛季切换 |

**必测的边界场景：**

- 赛季切换前最后一秒赢了一场 → 计入旧赛季还是新赛季？
- 榜单前 10 名中有人被封号 → 是否移除？替补玩家排名是否正确上移？
- 玩家改名后 → 榜单显示旧名还是新名？缓存多久更新？
- 合服时两服第一名积分相同 → 合服后谁是第一？

> 排名并列、赛季切换、封号移除——**这三个点是排行榜 bug 的富矿**，面试时主动提出来很加分。

## 四、其他专项

### Q5：如何测试多人在线游戏的网络稳定性？

模拟不同网络环境（延迟 100ms / 500ms、丢包 10% / 30%、断线重连），多人同时操作，观察同步和异常表现。

**要能说出工具**：Charles / Fiddler 限速、Network Link Conditioner（iOS）、弱网模拟器。

### Q6：如何测试内购/支付系统？

- **模拟完整流程**：发起 → 确认 → 成功 / 失败 / 取消
- **覆盖所有渠道**：微信 / 支付宝 / 苹果 / 各安卓渠道 SDK
- **三方核对**：客户端表现、服务端订单落库、渠道后台流水，**三者必须对得上**
- **异常场景**：断网支付、支付成功但回调失败、重复回调、退款
- **重点**：**支付成功但道具没到账** 是这类功能的致命问题，必须有补偿机制

### Q7：如何测试存档/读档？

- 在**不同状态下**存档：战斗中、副本中、挂机中、刚死亡时
- 重启游戏读档，验证数据一致、无丢失
- **跨版本升级后存档兼容性**（老存档在新版本能否正常读取）
- 多设备登录时，云存档的覆盖规则是否明确

### Q8：什么是压力测试？怎么做？

模拟**大量用户同时在线**，观察服务器和客户端的承载极限。

常用手段：机器人/自动化脚本模拟并发操作，逐步加压找到性能拐点。

**关键指标**：TPS、响应时间、错误率、CPU/内存曲线。**要能说出"找到拐点"这个概念**，而不是只说"压一压"。

## 小结

专项测试类题目的答题逻辑高度统一，都是这三步：

1. **定义清楚问题**（"卡"是哪一种卡？"没显示"是数据问题还是展示问题？）
2. **沿链路分层排查**（客户端 → 网络 → 服务端 → 数据库 → 展示层）
3. **给出可验证的动作**（不是"再看看"，而是"对比前后端日志的 X 字段"）

**这三步说出来，面试官就知道你是真排查过问题的。**
