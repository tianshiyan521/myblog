## 一、脚本就四块，这个骨架记住够用一辈子

任何公司的接口自动化框架，剥掉包装都是这四块：

| 块 | 名字 | 干什么 | 为什么重要 |
|---|------|------|-----------|
| ① | **用例表** `CASES` | 一条用例 = 一行数据 | 想加用例？加一行就行，不用改逻辑 |
| ② | **发请求** `call()` | 封装 requests，统一超时/异常 | 请求都从这一个口出去，好维护 |
| ③ | **断言** `check()` | 判断"对不对" | ⚠️ **不是判断"通没通"，这是自动化的灵魂** |
| ④ | **报告** `report()` | 汇总 + 把失败摊开讲清楚 | 报告是给人看的，不是给机器看的 |

**这四块的顺序不是随便排的。** 特别是 ③ 和 ①：

- 没有 ①，每加一条用例都要复制粘贴 20 行代码
- 没有 ③，脚本只能告诉你"请求发出去了"，不能告诉你"对不对"

## 二、块 ①：用例表

```python
CASES = [
    {
        "no": 9, "kind": "边界值",
        "title": "10 级领王者礼包 → 应该能领",
        "before": lambda: set_level(10),
        "req": ("POST", "/api/reward/claim", {"token": TOKEN, "rewardId": 2}),
        "expect": {"code": 0, "data.gold": 2000},
        "why": "★ 刚好等于门槛。手动测试最爱漏的就是「正好等于」这一个点。",
    },
]
```

**五个字段的设计意图：**

| 字段 | 作用 |
|------|------|
| `no` | 编号，报告里好引用、好跟 BUG 单关联 |
| `kind` | 测试点分类，最后能统计"覆盖了哪几类" |
| `before` | 前置动作，**让每条用例从同一个起点出发** |
| `req` | 请求三元组（方法、路径、参数） |
| `expect` | 期望值，**用 `a.b.c` 的路径表达嵌套字段** |
| `why` | **这条为什么值得测** —— 报告里会打出来 |

> 最后那个 `why` 字段是我特意加的。**写不出 `why` 的用例，说明你不知道为什么要测它**。这个字段能逼你把设计意图写清楚，也方便别人 review。

### 关于 `before`：用例隔离

```python
def reset():
    call("POST", "/api/gm/reset", {})

def set_level(n):
    reset()
    call("POST", "/api/gm/set_level", {"level": n})

def already_claimed(rid):
    reset()
    call("POST", "/api/reward/claim", {"token": TOKEN, "rewardId": rid})
```

**每条用例执行前，先把自己需要的环境造好。**

这是接口自动化里最容易出问题的地方。如果用例 A 创建的数据被用例 B 用掉了，那么：

- 单独跑 A → 通过
- 单独跑 B → 通过
- A、B 连着跑 → **B 挂了**

**这种"顺序依赖"是最难排查的自动化故障。** 解决方式只有一条：**每条用例自带前置，不依赖其他用例的副作用。**

## 三、块 ③：断言（自动化的灵魂）

这是第 1 课那个核心认知的落地。

```python
# ❌ 错误示范
assert r.status_code == 200

# ✅ 正确做法
expect = {"code": 0, "data.level": 5, "data.gold": 1000}
```

实现上，最难的部分是**从嵌套字典里按路径取值**：

```python
def dig(obj, path):
    """按 a.b.c 的路径，从嵌套字典里取值。取不到返回 (None, False)"""
    cur = obj
    for key in path.split("."):
        if isinstance(cur, dict) and key in cur:
            cur = cur[key]
        else:
            return None, False
    return cur, True


def check(body, expect):
    """逐项核对期望值，返回 (是否通过, 问题清单)"""
    if body is None:
        return False, ["响应体不是合法 JSON"]
    if "raw_error" in body:
        return False, ["请求根本没发出去：" + body["raw_error"]]

    problems = []
    for path, want in expect.items():
        got, found = dig(body, path)
        if not found:
            problems.append("%s  →  字段不存在" % path)
        elif got != want:
            problems.append("%s  →  期望 %r，实际 %r" % (path, want, got))
    return (len(problems) == 0), problems
```

**注意 `check()` 返回的是"问题清单"而不是布尔值。** 这个设计很关键：

- 返回 `False` → 报告里只能写"失败了"
- 返回 `["data.gold → 期望 2000，实际 1100"]` → **报告直接告诉你错在哪**

> **失败用例的报错必须能自解释。** 这是自动化脚本好不好用的分水岭——报告写得清楚，你一眼就知道是产品 bug 还是脚本写错；写得含糊，你就得去翻代码 debug。

## 四、11 条用例，覆盖 5 类测试点

| 编号 | 类型 | 用例 | 期望 |
|---|---|---|---|
| 1 | 正常流程 | 账号密码正确 → 登录成功 | code=0，拿到 token |
| 2 | 参数校验 | 密码错误 → 拒绝登录 | code=10001 |
| 3 | 参数校验 | 用户名为空 → 提示缺参 | code=20001 |
| 4 | 正常流程 | 带正确 token 查角色信息 | code=0，等级 5、金币 1000 |
| 5 | 鉴权 | token 错误 → 拒绝访问 | code=10002 |
| 6 | 正常流程 | 首次领新手礼包 | code=0，金币 1100 |
| 7 | 幂等 | 重复领新手礼包 | code=50003 |
| 8 | 边界值 | **5 级**领王者礼包 | code=50002 |
| 9 | 边界值 | **10 级**领王者礼包（刚好达标） | code=0 ← ❌ **挂了** |
| 10 | 正常流程 | 20 级领王者礼包 | code=0 |
| 11 | 参数校验 | rewardId 不存在（999） | code=20002 |

> 注意 **8、9、10 是同一个接口、同一个参数，只有等级不同。**
> **用例就是这么"设计"出来的：盯住一个变量，把它所有关键取值都走一遍。**

## 五、★ 那条失败的用例：一个真实的边界值缺陷

看报告里的原话：

```
实际回：{"code": 50002, "msg": "王者礼包需要 10 级，你当前 10 级"}
```

**请盯着这句话读三遍。**

> "王者礼包需要 10 级，你当前 10 级"

需要 10 级，我是 10 级，凭什么不让我领？

**这句报错本身就自相矛盾** —— 一个会说出这种话的程序，一定有问题。**这就是抓到了。**

去看服务端代码：

```python
if u_["level"] <= cfg["need_level"]:   # ← 问题在这
    return self._err(50002, f"王者礼包需要 10 级，你当前 {u_['level']} 级")
```

规则是"**10 级可以领**"，代码却写成了"**小于等于 10 级都拒绝**"。

**少了一个等号。10 级的玩家永远领不到这个礼包。**

### 为什么手动测很容易漏

手动测的时候，你很自然会试：

- 5 级 → 领不了 ✅ 符合预期
- 20 级 → 能领 ✅ 符合预期
- 然后觉得"没问题"了

但"**正好 10 级**"这个点，**得你特意去构造才会碰到**。而开发写错的，往往恰好就是这一个点。

> **边界上的人最少，出的事最多。**

## 六、从第 1 课到第 2 课，跨过的是什么

| | 第 1 课（手动点） | 第 2 课（脚本跑） |
|---|---|---|
| 谁发请求 | 你点按钮 | 脚本 |
| 谁判断对错 | 你的眼睛 | **代码里的断言** |
| 跑第二次 | 从头再点一遍 | 再点一次 bat |
| 记住结论 | 记脑子里 | 报告里，可留档可追溯 |

核心变化只有一句话：

> **从「看一眼觉得没问题」，变成「先写清楚什么样才算对」。**

后面那句话，就是**用例设计**。

用例表里每一条右边都写着一个明确的期望值 —— **那就是你脑子里的判断标准，被翻译成了代码。**

```
  ...
  9     边界值        ❌      10 级领王者礼包 → 应该能领
------------------------------------------------------------------
  合计 11 条   通过 10   失败 1
==================================================================

  🐛 发现 1 个疑似缺陷：
------------------------------------------------------------------
  [9] 10 级领王者礼包 → 应该能领
------------------------------------------------------------------
  打的是：POST /api/reward/claim
  发出去：{"token": "tk_abc123", "rewardId": 2}
  HTTP  ：200   ← 注意，这里通常也是 200
  实际回：{"code": 50002, "msg": "王者礼包需要 10 级，你当前 10 级"}

  问题：
    · code  →  期望 0，实际 50002

  这条为什么值得测：
    ★ 刚好等于门槛。手动测试最爱漏的就是「正好等于」这一个点。
```

**注意报告里那句 `HTTP ：200 ← 注意，这里通常也是 200`。**
这是刻意留在报告里的提醒——**每次看到失败用例的 HTTP 码是 200，都该提醒自己一遍：状态码不能作为通过标准。**

## 八、一个小但重要的细节：中文字符对齐

```python
def pad(s, width):
    """按显示宽度左对齐补齐（中文算 2 格，否则表格会歪）"""
    w = sum(2 if ord(ch) > 127 else 1 for ch in str(s))
    return str(s) + " " * max(0, width - w)
```

Python 的 `str.ljust()` 按**字符数**补齐，但中文在等宽字体里占 **2 格**。

不处理的话，报告里的表格会歪成一团——**这不是"美观问题"，是"可读性问题"**。报告是给人看的，看不清就是没写。

## 九、脚本还要自己管服务端

```python
def server_is_up():
    try:
        r = requests.get(BASE + "/api/ping", timeout=1)
        return r.json().get("data", {}).get("server") == "ok"
    except Exception:
        return False
```

**交付给别人用的脚本，要做到"双击一个文件全跑完"。**

先探测服务端在不在 → 不在就自己启 → 跑完自己关。使用者的操作应该是**双击一个 bat**，不是"先启动服务端，再跑脚本，再关掉"。

> 这个原则是我交付脚本时踩过坑总结的：只要让人做超过一步，就会有人做错。
